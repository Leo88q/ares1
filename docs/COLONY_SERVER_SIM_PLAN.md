# Колония: серверная симуляция и оплата POTATO (план)

Статус: **F1–F3 выполнены** (см. «Выполнено»). F4 (клиент) и F5 (devnet) не начаты. Текущие гейты не меняются:
`VITE_COLONY_POTATO_SPEND=false`, `COLONY_POTATO_SPEND_ENABLED=false`, mainnet закрыт до отдельного GO.

## Решения владельца

- **Курс сжигания (вариант B): 1 POTATO = 1 CR.** Стройка и ремонт стоят столько POTATO, сколько CR сейчас.
  Стартовый бюджет остаётся в CR и не конвертируется в POTATO (без эмиссии, см. `COLONY_V1_PRODUCT_PROPOSAL.md` §47).
- **Авторитетное состояние: вариант 2, симуляция целиком на сервере.** Клиент шлёт действия и показывает
  состояние, которое вернул сервер. Локальная мутация состояния запрещена.
- Квитанция сбоя (сожжено, колония не изменилась): сообщение и обращение в поддержку (уже реализовано).

## Проверено (2026-11-06)

- Замыкание движка `colony/simulation.ts` ≈ 7 900 строк (simulation, networks, layout, organism/*, deep/*).
  В нём нет React, three, DOM, `Date`, `Math.random`; RNG детерминированный (mulberry32 с seed).
- Прогон в Node (построения, 30 + 45 + 90 дней, ремонт, припасы, поставка) дважды даёт одинаковый SHA-256 состояния.
- Размер состояния (JSON): 24 КБ в начале, 178 КБ через 90 дней, 369 КБ через 365 дней.
- Время прогона: 90 дней ≈ 545 мс, 365 дней ≈ 1,8 с. Сервер не может перематывать год одним запросом.

## Архитектура

1. **Пакет движка.** Вынесено в vendor-пакет `game/apps/web/vendor/colony-engine` (`@ares/colony-engine`), а не в `packages/`: Cloudflare Pages видит только `game/apps/web`. Web и backend импортируют его.
   Web-файлы на время миграции реэкспортируют старые пути, чтобы не менять десятки импортов сразу.
2. **Действия.** Каждая мутация UI становится типизированным действием: `build`, `move`, `repair`, `supplies`,
   `deliver`, `harvestBed`, `advanceDays(n)` (n ≤ 7 за запрос), сетевые действия, действия deep-панелей, `reset`.
   Сервер применяет `applyAction(state, action)` и возвращает новое состояние.
3. **Хранение.** Журнал + периодические снимки, а не один большой JSON на каждый шаг:
   - `colony_sim_sessions(owner_wallet PK, sequence, snapshot_sequence, snapshot text, state_hash, engine_version, updated_at)`;
     снимок — `text`, а не `jsonb`: jsonb переупорядочивает ключи, а хеш и воспроизведение зависят от порядка;
   - `colony_sim_actions(owner_wallet, sequence, request_id UNIQUE, action jsonb, state_hash, engine_version, created_at)` — append-only
     (триггеры `deny_mutation`, как в миграции 0017).
   Версия движка записывается в каждую строку, чтобы изменение правил не ломало воспроизведение журнала.
4. **API.**
   - `GET /api/colony-sim/state` — текущий снимок и `sequence`.
   - `POST /api/colony-sim/actions` — `{requestId, expectedSequence, action, spendSignature?}`.
     Идемпотентность по `requestId`; несовпадение `expectedSequence` → 409 с актуальным состоянием.
5. **Оплата.** Действия стройки и ремонта требуют `spendSignature`. В одной транзакции сервер:
   - проверяет квитанцию `colony_potato_spends` (владелец, назначение, сумма = цена в CR × 1);
   - вставляет `colony_spend_consumptions(signature PK, request_id)` (append-only) — повторное использование невозможно;
   - применяет действие и пишет журнал.
   Порядок для клиента: подпись `colony_spend` → квитанция → действие с `spendSignature`.
6. **Клиент.** Состояние только с сервера. Во время запроса кнопки заблокированы. На 409 — перечитать состояние.
   Локальные сохранения колонии не переносятся автоматически; новый кошелёк стартует с серверного снимка.
7. **ColonyService** (metal/water/power/science, SKR) — отдельная модель. В этих шагах не трогаем.
   Оставить или удалить после перехода — отдельное решение владельца.

## Фазы

- **F1.** Пакет движка, тест детерминизма в CI (два прогона одного журнала → одинаковый хеш).
- **F2.** Миграция 0018 (сессии, журнал, потребление квитанций), `applyAction` на сервере, тесты на PGlite.
- **F3.** API, проверка квитанции в транзакции, тесты: повтор, 409, сожжённая квитанция, чужой кошелёк.
- **F4.** Клиент переходит на серверное состояние, локальная мутация удаляется, browser smoke.
- **F5.** Devnet-прогон, замер нагрузки и размера снимка, решение по хранению больших снимков (сжатие).

## Риски

- Рост снимка (~370 КБ в год): при необходимости сжимать; журнал остаётся основным источником истины.
- Стоимость прогона на сервере: лимит дней за запрос; тяжёлые прогоны — только по запросу, не по таймеру.
- Изменение правил движка меняет результат старого журнала: нужна версия движка и миграция журнала.
- Пока F4 не закрыт, 3D-колония остаётся в браузере, и POTATO-оплата не защищает состояние. Поэтому
  флаги `VITE_COLONY_POTATO_SPEND` и `COLONY_POTATO_SPEND_ENABLED` остаются выключенными до F4.

## Остаток (F4, F5)

- **F4.** Клиент: общий хук входа по кошельку (вынести из `PersistentColonyPanel`), `simApi` с `requestId` (UUID),
  режим `VITE_COLONY_SIM` (по умолчанию выключен). В этом режиме `ColonyContext` берёт состояние с сервера,
  а все мутации (`ColonyScreen`: ремонт, стройка, перенос, урожай, припасы, поставка, тик времени;
  `NetworkPanel`; 13 прямых вызовов `world` в `DeepPanels`) уходят через `act(action)`. Локальная мутация
  в этом режиме не допускается. Локальный режим до включения флага **сохраняется** (решение: иначе /base
  ломается при выключенном флаге). Удаление локального режима — отдельное решение владельца.
- **F5.** Devnet-прогон, замер нагрузки и размера ответа, решение о сжатии. Требует devnet RPC и CI;
  из песочницы недоступно.

## Ограничения, которые остаются открытыми

- Стройка и ремонт — единственные действия, которые оплачиваются POTATO (как в клиенте до этого).
- Ответ `act` возвращает полное состояние (до ~370 КБ при полном годе). Дельта — отдельная оптимизация.
- Если версия движка в журнале не совпадает с текущей, загрузка отказывает (`ENGINE_VERSION_MISMATCH`).
  Миграция журнала под новые правила — отдельное решение; автоматической нет.
