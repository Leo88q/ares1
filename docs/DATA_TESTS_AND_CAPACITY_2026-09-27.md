## 2. Как устроены данные

### 2.1 Ончейн — единственный источник правды

Всё игровое состояние живёт в аккаунтах программы `solana_potato`: `GameConfig` (singleton PDA `[b"config"]`),
`Epoch` (`[b"epoch", epoch_id]`), `Field`, `Order` (`[b"order", order_id]`), `Referral`, `Achievement`,
`AdminState`, `PresaleBuyer` и т. д. Раскладки версионируются через `migrations.rs` (белый список
размеров; тест `tests/offchain/migrations.test.ts` + host‑тест «актуальные размеры — последние в списке»).

Что важно для нагрузки и архитектуры (проверено по коду):

* `harvest` (и `batch_harvest`) пишет **шесть** аккаунтов: `config` (mut), `epoch` (mut), `field` (mut),
  mint, ATA игрока, ATA казны (`programs/solana_potato/src/lib.rs:2355`). Первые два — **общие для всех
  игроков**.
* Эмиссия ограничена сверху: кап эпохи ≤ `3 × daily_mint_cap_micro`, гранты ≤ 10 % капа, `max_supply`.
* Вывод из казны — двухшаговый (propose → 30 с → execute) с окнами 250 000 POTATO / 25 SOL /
  100 000 SKR за 24 ч (константы `MAX_WITHDRAW_*_PER_WINDOW`).
* Все действия идемпотентны по PDA‑ключу: `["field", field_id]`, `["order", order_id]`,
  `["buyer_presale", buyer]` — повтор невозможен конструктивно (`init` на существующем PDA падает).

### 2.2 Офчейн — read‑model Watchtower (единственная БД)

`watchtower/migrations/watchtower-read-model.sql` (schema_version = 1, повторный запуск безопасен):

| Таблица | Зачем | Ключи/ограничения |
|---|---|---|
| `transactions` | финализированные транзакции | PK `(cluster, signature)`, `commitment='finalized'` CHECK, `fingerprint` sha256 |
| `raw_events` | одна строка = один invocation, все `emit!` в `payload` (jsonb) | UNIQUE `(cluster, slot, signature, instruction_index, inner_index)`, FK → `transactions` |
| `normalized_events` | разобранные события (30 типов из IDL) | UNIQUE `(raw_id, log_index)`, индексы `(event_type, id)` |
| `cursors` | позиция ingest + CAS `version` + row lock | PK `stream_id` |
| `reconciliation_state` | watermark сверки c finalized | PK `stream_id` |
| `data_quality` | открытые gap/ошибки (влияют на `/readyz`) | PK `(stream_id, code)` |
| `audit_records` | аудит изменений курсора/реконсиляции | — |
| `daily_projections` (view) | суточные счётчики событий | view, а не инкрементальный счётчик → replay не удваивает |

Инварианты слоя (проверено тестами, часть — против настоящего PostgreSQL, см. §3.3):

* страница ingest (raw + normalized + audit + cursor) пишется **одной** транзакцией; обрыв → откат целиком;
* курсор защищён CAS + `SELECT … FOR UPDATE`, конкурентный stale‑писатель получает `STALE_CURSOR`;
* изменившийся finalized‑fingerprint → `FINALIZED_RECONCILIATION_MISMATCH` (fail‑closed), а не перезапись;
* события откатившихся транзакций сохраняются с `applied=false` и исключены из проекций;
* unknown‑события не выбрасываются: `parserVersion=ares1-raw-v1`, сырой payload в `raw_events`.

**Чего в БД нет:** балансов игроков, офчейн‑прогресса, лидербордов, платёжной истории. Индексатор
никогда не пишет ончейн и не имеет ключей (`WATCHTOWER_ENABLE_WRITES` принимается только как `false`;
отдельный bearer‑токен ≥ 32 символов; allowlist read‑методов RPC).

### 2.3 Клиент и бэкенд

* `game/apps/web`: в `localStorage` — флаг туториала, кэш адреса lookup table, язык, настройки
  уведомлений. Никаких игровых цифр, которые можно было бы подделать в браузере.
* `game/apps/backend`: БД не использует вовсе (`OPERATIONS.md`: «The backend currently has no
  persistent history/database»). Хранит только ключ низкопривилегированного payer'а для `roll_epoch`.
* `landing/`: статика, персональных данных не хранит.

## 5. Какую нагрузку выдержит игра

### 5.1 Ончейн — реальное ограничение

Ключевой архитектурный факт: `harvest`/`batch_harvest` пишут в **общий** `epoch`‑PDA и **общий**
`config`‑PDA. Solana сериализует транзакции, пишущие в один аккаунт (внутри слота они выполняются
последовательно), поэтому все сборы всех игроков конкурируют за два аккаунта.

| Ограничение | Следствие |
|---|---|
| Общий `epoch` + `config` на каждый harvest | потолок не по числу игроков, а по числу **транзакций сбора**, попадающих в блок: ~2.5 слота/с × лимит блока по CU. При ≈40–60k CU на harvest и лимите блока 48M CU — порядка **800–1200 harvest‑транзакций на блок** (≈2–3 тыс./с теоретически), но латентность каждого игрока растёт с конкуренцией за аккаунт |
| `batch_harvest` ≤ 10 полей за транзакцию | 10 сборов за одну транзакцию → эффективность по аккаунтам ×10; это и есть штатный способ масштабирования |
| Кап эмиссии эпохи (`≤ 3 × daily_mint_cap_micro` = ≤ 750 000 POTATO/сутки по умолчанию) | ограничивает суммарный урожай в день независимо от числа игроков |
| Интервал сбора 60 с, окно накопления 7 суток | фоновый потолок: один игрок не может «прокрутить» больше 1 сбора/минуту/поле |
| Комиссия сети + rent нового epoch‑аккаунта (~0.0013 SOL/эпоху) | крон‑роллер эпохи платит с отдельного кошелька; выведен из подписи authority (`assertDedicatedPayer`) |

**Практический вывод:** до тысяч одновременных игроков узким местом будут (а) общий epoch‑аккаунт,
(б) потолок эмиссии, а не фронтенд, не API и не индексатор. Рекомендации (не реализованы, это гейт):
шардировать эпоху/аккаунты учёта, штатно использовать `batch_harvest`, заранее считать SLO по
латентности при конкуренции за `config`.

### 5.2 Офчейн — измеренные пределы

* **Статический фронтенд:** сборка `ci-local.sh` — основной чанк 310 kB (gz 120 kB), solana 327 kB
  (gz 95 kB), vendor → CDN/статик‑хостинг масштабируется независимо от игры.
* **Read‑only API бэкенда:** rate limit по умолчанию 30 запросов/мин на IP (`RATE_LIMIT_PER_MINUTE`),
  `/live` не лимитируется (это healthcheck). `trust proxy` по умолчанию `1` — за одним прокси верно, но
  при прямом выставлении API `X-Forwarded-For` позволяет обойти лимит (предупреждение уже в коде;
  безопасная настройка — `TRUST_PROXY=false`).
* **Индексатор:** 254 tx/s (505 событий/с, 1 014 строк/с) на WASM‑Postgres — это **нижняя граница**;
  на нативном PostgreSQL ожидаемо выше, узкое место — последовательный `getTransaction` по каждому tx
  и запись в одной транзакции на страницу.
* **Readiness как защита от «зелёного» при сбое:** `/readyz` = 503, пока есть хоть одна нерешённая
  запись в `data_quality`; данные не «доиспользуются» при gap. Проверено: на необработанном gap
  сервис не становится ready даже при успешном ingest.

### 5.3 Что выдержит игра — итог

| Слой | Предел (оценка) | Чем ограничен |
|---|---|---|
| Декодер событий | ≈12 000–14 500 tx/с / ≈24 000–29 000 событий/с | CPU одного процесса Node |
| Запись read‑model | ≥254 tx/с (нижняя граница), растёт на нативном PG | последовательные запросы + 4 INSERT на tx |
| HTTP API индексатора | десятки мс/запрос; конкурентный RPS не измерен | однопоточный PGlite в песочнице |
| Ончейн‑игра | ~1 000 harvest‑транзакций на блок, ×10 при `batch_harvest` | общий `epoch`/`config` PDA + кап эмиссии |
