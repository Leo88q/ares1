# Ротация скомпрометированного ключа (S-01)

Документ для владельца ключа. Кодом это не лечится: удаление файла из репозитория
не удаляет ключ из истории git, а репозиторий публичный. Пока ключ действует,
любой, кто склонировал репозиторий раньше, может им пользоваться и жечь чужую
квоту (или получить доступ к RPC-аккаунту).

## Что известно

| Поле | Значение |
|---|---|
| Правило сканера | `helius-key-in-url` |
| Файл | `game/apps/web/.env.production` (удалён из рабочего дерева, лежит в истории) |
| Коммиты | `55ba9d9` … `87eb954` |
| Что за ключ | Helius **devnet** RPC API key |
| Публичность | Репозиторий публичный; считать ключ известным всем |
| Состояние | `.secret-rotation-status.json` → `S-01.status` |

## Почему CI красный и почему это правильно

`scripts/secret-scan-history.mjs` сканирует **все** объекты `--all`. Запись в
`.secret-scan-allowlist.json` для этого пути была помечена «NOT ALLOWLISTED»:
allowlist — это «здесь не секрет», а здесь секрет **был**. Поэтому появился
`.secret-rotation-status.json` — отдельный реестр ротаций. Сканер читает его
так:

* `revoked=false` → находка остаётся, job `Secret scanning` красный (сигнал);
* `revoked-at=<ISO-дата>` → конкретный путь и правило перестают считаться
  находкой;
* `no-longer-valid` → у провайдера проверено, что ключ ничего не выдаёт.

Гейт нельзя «успокоить» правкой allowlist. Нельзя и переписать историю: это
отдельное решение владельца, и оно не входит в эту ветку.

## Порядок действий (делает владелец ключа)

1. **Отозвать ключ** в панели Helius (API Keys → Revoke) и посмотреть usage и
   billing за период после коммита `55ba9d9`: неожиданные запросы = ключом
   пользовались.
2. **Выдать замену с ограничениями**: новый ключ, привязанный к домену/origin
   приложения, отдельный от серверных ключей. Серверный ключ никогда не попадает
   в `VITE_*`: всё с этим префиксом уезжает в браузерный бандл.
3. **Разложить по местам хранения**: ключ живёт только в переменных окружения
   панели хостинга (Cloudflare Pages / Vercel) и в секретах CI. Не в
   `.env.production`, не в README, не в чате.
4. **Записать ротацию** в `.secret-rotation-status.json`:

   ```json
   "S-01": { "status": "revoked-at=2026-11-06 (usage checked, replacement limited to the app origin)" }
   ```

   Дата обязательна: `revoked` без `revoked-at=` сканер не засчитывает.
5. **Прогнать скан локально** (нужен полный клон, не `--depth 1`):

   ```bash
   git fetch --unshallow origin    # если клон shallow
   node scripts/secret-scan-history.mjs
   ```

   Ожидаемый результат: `history: no findings` и строка
   `rotation S-01: … — закрыто (revoked-at=…)`.
6. **Только после этого** гейт в `.github/workflows/security.yml` станет зелёным
   без изменения кода.

## Переписывание истории

Не выполняется в этой ветке и не требуется для закрытия утечки: после отзыва
ключа историческая копия бесполезна. Если владелец всё же решит чистить историю
(`git filter-repo`), это ломает все клоны и хеши коммитов, требует force-push во
все ветки и отдельного объявления — и должно идти **после** шага 1, а не вместо
него.

## Проверки в CI

* `Secret scanning` → шаг `Full history scan` (жёсткий, красный до ротации).
* `Secret scanning` → шаг `Working tree` — ключа в текущем дереве нет и быть не
  должно; `.gitignore` держит `.env*`.
* `Deploy readiness` → `.gitignore covers secrets, keys and dumps`.
