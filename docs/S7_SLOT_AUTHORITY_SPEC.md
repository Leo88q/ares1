# S7: авторитет владения слотами (спецификация, черновик на ревью)

Статус: **черновик, код не написан.** Этот документ нужен до реализации, как и просил владелец. Решения владельца берутся из `ORGANISM_INTEGRATION.md` §18–§19 и помечены «решено». Всё остальное помечено «предложение» и не вступает в силу без подтверждения.

## 1. Что уже решено владельцем

| Что | Значение | Источник |
|---|---|---|
| Потолок слотов на поле (S3) | 12 | §19 |
| Бесплатные слоты | первые 6 | §19 |
| Цена слота 7–12 | 500 SKR каждый | §18, §19 |
| Авторитет владения (S7) | **подписанная запись сервера**, не on-chain аккаунт поля | §19 |
| Грядка на слоте | покупается в POTATO по цене поля того же тира | §18 |
| Выход урожая | идёт через программу и существующие механики; запись сервера не даёт прямого выхода POTATO | §19 |

Следствие: владение слотом хранится на сервере. Программа Solana о слотах не знает и не меняется этим документом.

## 2. Что такое запись слота

Запись подтверждает одно утверждение: «кошелёк `W` вправе занять слот `N` на поле `F` до времени `T`».

Поля (предложение):

- `v`: версия формата, `1`.
- `field_id`: идентификатор поля.
- `slot`: индекс слота, `7..12` (слоты 1–6 бесплатны и тоже выдаются записью с `payment_signature = null`).
- `wallet`: base58-адрес владельца.
- `nonce`: уникальный идентификатор записи (UUID v4).
- `issued_at`, `expires_at`: unix-время. Срок действия записи — 24 часа (предложение). Записи с истёкшим сроком не принимаются клиентом.
- `payment_signature`: подпись транзакции SKR-платежа; для бесплатных слотов `null`.
- `key_id`: идентификатор ключа подписи (см. §5).

Подпись: ed25519 над канонической JSON-строкой. Канонизация — `stableStringify` из `gameops/audit.ts`, уже используется в проекте. Так подпись не зависит от порядка полей.

## 3. Проверка платежа SKR

Правило, которое уже есть для presale (`presale/verify.ts`): сомнительный платёж не засчитывается автоматически, а уходит в ручную очередь с кодом отказа. Проверка делается по снимку транзакции, полученному сервером из RPC, а не по данным клиента.

Условия засчитывания (предложение):

1. Транзакция существует и `meta.err == null`.
2. Уровень подтверждения — `finalized` (предложение; вопрос ниже).
3. Есть перевод SKR на казначейский токен-аккаунт тиража точно на сумму 500 SKR (в базовых единицах mint'а).
4. Источник перевода принадлежит `wallet` (владелец токен-аккаунта совпадает с кошельком из записи).
5. `blockTime` не раньше момента создания заказа на слот (защита от старых переводов).
6. Подпись транзакции **не использована ранее** ни для одного слота (см. §4).

Mint SKR и адрес казначейства берутся из конфигурации окружения, в документе они не фиксируются.

## 4. Защита от повторов

- Один платёж — один слот: уникальный индекс на `payment_signature` в таблице выдачи.
- Один `nonce` — одна запись: уникальный индекс на `nonce`.
- Слот на поле занимается однозначно: уникальность `(field_id, slot)` среди действующих записей.
- Запись не переиспользуется между кошельками: `wallet` входит в подписываемое сообщение.

## 5. Ключ подписи и ротация

- Ключ подписи хранится вне репозитория (секрет окружения оператора), в Git и логах не появляется.
- Каждый ключ имеет `key_id`. Публичные ключи публикуются в конфигурации клиента.
- Ротация: новый ключ добавляется в список принимаемых до того, как начинает подписывать. Старый выводится через 7 дней (предложение). Это совпадает с логикой таймлока параметров экономики (§12.5).
- Компрометация: немедленное удаление ключа из списка принимаемых и перевыпуск записей, подписанных им.

## 6. Журнал и аудит

- Таблица `slot_grants` — append-only: запись не меняется и не удаляется, отзыв — новой строкой.
- Каждое решение (выдача, отказ, ручная очередь) пишется через `recordAudit` (`gameops/audit.ts`) с исходом `ok | denied | error`.
- Аудит-выборка: по кошельку, по полю, по `payment_signature`.

## 7. Что это не делает

- Не меняет программу Solana и не добавляет слоты в on-chain состояние.
- Не даёт прямого выхода POTATO: выход на слоте ограничен инфраструктурой колонии (K-C, §14.6).
- Не вводит минт и не меняет эмиссию.
- Не включает mainnet и не трогает `PRESALE_MAINNET_LIVE_APPROVED`.

## 8. Открытые вопросы (нужны владельцу)

1. **Уровень подтверждения** для засчитывания: `finalized` (предложение, надёжнее) или `confirmed` (быстрее).
2. **Срок записи** 24 часа — подходит ли.
3. **Ротация** — 7 дней на вывод старого ключа, достаточно ли.
4. **Отзыв слота** — допускается ли отзыв (например, при мошенничестве) и как он компенсируется.
5. **Ручная очередь** — кто оператор, и кто подтверждает спорные платежи.
6. **Цена при сбое** — что происходит, если платёж прошёл, а запись не выдана (возврат SKR или повтор выдачи по той же подписи).

## 9. План реализации (после решений владельца)

1. Миграция `slot_grants` с уникальными индексами (§4) и тестами миграции (`game_ops DB` в CI).
2. Чистая функция проверки платежа по снимку транзакции (по образцу `presale/verify.ts`), тесты на каждый код отказа.
3. Функция канонизации и подписи записи, тесты на стабильность подписи и на отказ при изменённом поле.
4. Эндпоинт выдачи, за флагом. По умолчанию выключен.
5. UI покупки слота за флагом (`VITE_SLOTS_ENABLED`, по умолчанию `false`).
6. Прогон на devnet оператором. Mainnet — только после GO/NO-GO владельца.

Пункты 2–3 можно начать без ответов на вопросы 4–6: они не меняют формат записи.
