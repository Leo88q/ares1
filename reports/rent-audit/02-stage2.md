# Этап 2 — доказательная база: из чего состоит `.so` и сколько стоит код в CU

Этап 1 дал цены срезов (профили, группы инструкций, SBPF v3), но оставил
открытым вопрос «а нет ли в `.so` лишнего, что можно убрать без изменения
продукта». Этап 2 отвечает на него измерениями в CI:

* **`ares-elf-audit`** — что физически лежит в задеплоенном файле: сходимость
  размера, энтропия/gzip по секциям, наличие таблиц символов и отладочных
  секций, содержимое `.rodata` (строки, маркеры panic/путей);
* **`ares-usage`** — какие из 44 инструкций вообще упоминаются слоями клиента
  (UI / утилиты web / backend / тесты / скрипты);
* **`ares-cu`** — compute units каждой инструкции на localnet (лог `anchor test`).

Канонический полный прогон: **Rent audit CU**, run
[36919450348](https://github.com/Leo88q/ares1/actions/runs/36919450348), рев
`a17b038`, job/check-run `110561535903` (успех; `opt-level=z`, Anchor localnet tests
пройдены). Из этого check-run прочитаны все четыре полезные аннотации
(`ares-elf-audit`, `ares-usage`, `ares-cu`, `ares-cu-2`); полные CU-строки и
развёрнутый coverage JSON сохранены в `evidence/`.

История измерителя: run `36908445497` сначала дал `measured:false`, потому что
CU-скрипт смотрел только stdout; run `36909890303` уже читал
`.anchor/program-logs`, но одна аннотация обрезалась; `c3a40b0` починил разбиение.
В нескольких успешных повторах меняются количество вызовов и CU-выборки, поэтому
таблица §3 — полный срез **конкретного** последнего прогона, не детерминированная
константа для каждого входа.

## 1. В задеплоенном `.so` нет ничего, кроме кода

`ares-elf-audit` (756 424 Б, sha256 `25ba34d7…` — тот же файл, что в этапе 1):

| Проверка | Измерено | Вывод |
|---|---|---|
| Сходимость размера | секции на диске 755 558 + заголовки 864 (ELF 64 + 4×56 program + 9×64 section) = 756 422 при файле 756 424 | расхождение **2 Б** (выравнивание) — в файле нет ни байта «сверх» ELF |
| Таблицы символов | `.symtab` нет, `.strtab` нет, `.debug*` нет; `.dynsym` 432 Б | strip уже сделан `build-sbf`; срезать имена нечем |
| Энтропия секций | `.text` 3,58 бит/Б (gzip 0,22); `.rel.dyn` 2,19 (0,13); `.rodata` 5,72 (0,44); `.data.rel.ro` 2,50 (0,21) | случайных/сжатых вставок нет (у данных было бы ≈8,0/≈1,0) — весь объём объясняется кодом |

Состав файла: `.text` 659 240 (87,1 %) + `.rel.dyn` 58 880 (7,8 %) +
`.rodata` 21 936 (2,9 %) + `.data.rel.ro` 14 552 (1,9 %) + служебные 950 (0,1 %).
**96,9 % — код и перемещения.**

Строки `.rodata`: 114 строк длиной ≥ 4 Б, из них 17 268 Б печатных (79 %
секции) — это `require!`-сообщения, `msg!` и формат-строки Anchor. Маркеры:
`panicked at` — 1, `src/` — 36, `unwrap` — 3. Отсюда **верхняя граница**
экономии на «тексте»: даже если убрать все сообщения до одного байта, это
≤ 17 268 Б = **0,088 SOL** при ставке 5080, и это уже не оптимизация, а
изменение UX/ABI. Остальные ≈ 210 КБ требуемого среза — только код.

## 2. Покрытие инструкций клиентскими слоями (`ares-usage`)

IDL содержит 44 инструкции. `ares-usage` ищет статические имена в шести слоях:
`web-ui`, `web-builder` (`apps/web/src/utils/anchorClient.ts`), `web-utils`,
`backend`, `tests`, `scripts`. Комментарии удаляются; поддерживаются имена snake,
camel/Pascal и `ix`+Pascal, чтобы видеть обёртки вида `ixMigrateAdminState`.
**Числа ниже — количество уникальных имён инструкций с хотя бы одним совпадением
в слое; слои перекрываются, поэтому числа не складываются в 44.** Совпадение в
строке/коде не доказывает runtime-вызов; динамические и внешние клиенты не
видны. `programs/`, IDL и сгенерированные `types/**` исключены.

| Слой | Имен инструкций с совпадением |
|---|---:|
| `web-ui` | 16 |
| `web-builder` | 27 |
| `web-utils` | 6 |
| `backend` | 8 |
| `tests` | 43 |
| `scripts` | 14 |
| **без совпадений во всех сканируемых слоях** | **1: `withdraw_skr_treasury`** |

Факты для вопросов:

* `buy_field_sol`: есть имя в `web-builder` и тестах, **нет** в `web-ui`. Это
  подтверждает узкую формулировку «не подключён в UI», но не означает, что
  инструкцию нельзя вызывать внешним клиентом. Вариант удаления ещё надо
  отдельно измерить в Этапе 3 перед Q4.
* `grant_reward`: найден в `backend`, `tests`, `scripts`; в UI и builder его нет
  (совпадение в старой версии было комментарием и теперь отфильтровывается).
  Измеренный `no-grant` Этапа 1 убирал **обе** инструкции,
  `grant_reward` + `grant_reward_once`, поэтому −26 824 Б / −0,1365 SOL — цена
  пары по `NEED_TOTAL`, а не изолированная цена `grant_reward`. Для Q3 нужна
  отдельная CI-вариация, сохраняющая `grant_reward_once`.
* `migrate_admin_state` находится в builder и тестах (обёртка `ix`); это не
  доказанно мёртвый код, хотя прямого UI-упоминания нет.
* `withdraw_skr_treasury` — единственное имя без совпадений в сканируемом коде;
  инструкция остаётся в ABI/документации, а тест содержит лишь комментарий,
  что localnet-проверка не делается из-за константного `SKR_MINT`. Это кандидат
  на ручную проверку, **не** основание для удаления: внешний администраторский
  клиент не сканируется. ABI/экономика не менялись.

Итого: покрытие не доказывает «dead code». Миграции и рельсы наград требуют
решения человека (Q2/Q3), а `buy_field_sol` — отдельного измерения размера до
вопроса Q4. Полный результат по каждой инструкции и путям файлов:
`evidence/02-usage-details.json`; сводка, совпавшая с CI-аннотацией, —
`evidence/02-usage.json`.

## 4. Выводы этапа 2

1. В `.so` нет `.symtab`/`.debug*`; энтропия и сходимость размера не выявили
   удаляемых метаданных. Даже полное удаление печатного `.rodata` ограничено
   17 268 Б (≈0,088 SOL при 5080), лишь 7,6 % от нужных 227 017 Б. Порог A
   потребует сокращать код.
2. Статический обзор нашёл один кодовый кандидат без внутренних ссылок
   (`withdraw_skr_treasury`), но это не доказывает его ненужность для внешнего
   клиента. Никакие инструкции/ABI не удалялись. `buy_field_sol` и
   `grant_reward*` имеют конкретные места в builder/backend/tests; решения — за
   владельцем продукта.
3. Для CU все значения в текущем прогоне ниже 65 520/200 000; минимальный запас
   по наблюдаемому максимуму — около 3,05×. Проблемы CU в измеренных путях нет,
   но профиль — выборка теста и меняется между повторами.
4. Доказанные размерные рычаги Этапа 1 остаются: `opt-level=z` (−22,1 % к base),
   группа M (−27 152 Б / −0,1382 SOL по `NEED_TOTAL`), совместное удаление
   `grant_reward` и `grant_reward_once` (−26 824 Б / −0,1365 SOL), SBPF v3
   (−60 016 Б / −0,3054 SOL). `no-m`/`no-grant` — CI-эксперименты без
   сохранения ABI, а `arch-v3` меняет целевую платформу; ни один не готов к
   мерджу без отдельного решения. Для Q3/Q4 надо изолировать варианты и
   получить отдельные цифры.
