# Mainnet launch gate — ARES-1

Чек-лист 31–70: организационные пункты, которые нельзя закрыть кодом
(44, 45, 62–65, 67, 68 и гейты на будущую функциональность).
Статус: **mainnet не запущен, gate не пройден.** Документ — обязательный
проход перед тем, как программа получит реальные средства.

Машино-проверяемая часть автоматизирована: `scripts/preflight-mainnet.sh`
(падает с exit 1 при нарушении) и `scripts/check-invariants.ts` (крон/мониторинг).

## G-0. Порядок прохода

```sh
cd game
anchor build                       # reproducible: сравнить sha256 двух сборок
PROGRAM_ID=<id> \
MAINNET_AUTHORITY=<squads-vault> \
MAINNET_TREASURY=<treasury-owner> \
MAINNET_PAYER=<backend-hot-wallet> \
POTATO_MINT=<mint> \
RPC_URL=<mainnet-rpc> \
  ./scripts/preflight-mainnet.sh --expected-so-sha256 <hash-reviewed-build>
```

Скрипт проверяет: программа существует; upgrade authority — ожидаемый мультисиг
и не совпадает с hot-wallet/владельцем казны; артефакт сборки совпадает с
рассмотренным хешем; трипваер защит зелёный. Всё остальное — в этом файле,
под подпись ответственного.

## G-1. Рельс выплат (`grant_reward`) — включить только с nonce-PDA

**Сегодня:** рельс собран (`buildGrantRewardIx`), но не подключён ни к одному
эндпоинту; ущерб от угнанного `reward_signer` ограничен 10 % капа эпохи.

**Условие включения** (чек-лист п. 41 — replay выплат):

1. Инструкция `grant_reward_once(nonce: u64, amount_micro: u64)` с аккаунтом
   `reward_claim` = PDA `["reward", recipient_ata, nonce]`, создаваемым через
   `init` → повторная выплата по тому же nonce физически невозможна.
2. Бэкенд хранит одноразовый `nonce` + `expiry` для каждой награды; заявка без
   nonce или с истёкшим expiry отклоняется.
3. `reward_signer` — выделенный ключ, не authority (уже так), лимит на сутки
   ниже квоты 10 % капа.
4. Мониторинг: алерт на любое превышение планового числа грантов за час.

Без пунктов 1–2 эндпоинт наград **не открывать**: это ровно тот класс багов,
на котором Aurory потерял ~600k токенов (гонка/повтор оффчейн-запросов).

## G-1b. Durable nonce и социальная инженерия подписантов (п. 82)

Прецедент 2026 года — Drift Protocol ($285–286M, 1 апреля 2026): двух из пяти
подписантов мультисига социально проинженерили подписать **durable-nonce**
транзакции заранее; такая подпись не истекает, как обычная (recent blockhash), и
атакующий предъявил её позже, замаскировав под рутинную операцию.

Правила (действуют для authority-мультисига, Squads-предложений и любых
подписантов программы):

1. **Подпись durable-nonce транзакции = подпись обычной транзакции.** Никогда не
   подписывать «на всякий случай, это рутина» без проверки: программа, все
   инструкции, все аккаунты, суммы и получатели. Незнакомая durable-nonce
   транзакция отклоняется без обсуждения.
2. **Таймлок не обнуляется.** Смена состава мультисига / Security Council,
   апгрейд upgrade authority и миграция программы — только с таймлоком ≥ 24 ч
   (совпадает с `ADMIN_UPDATE_TIMELOCK_SECONDS`) и «окном отмены». «Срочные
   обстоятельства» из чата/телеграма не сокращают таймлок.
3. **Мониторинг.** Отдельный алерт на: создание durable-nonce аккаунта для адресов
   команды, `AdvanceNonceAccount`, предложения Squads вне обычного окна, изменение
   порога/состава мультисига. Проверять перед каждой подписью: `nonce account` не
   пересоздавался, в предложении ровно те инструкции, что обсуждались.
4. **Проверка полезной нагрузки вне интерфейса.** Симуляция в клиенте Squads — не
   доказательство: подписывающий декодирует инструкции (`describeInstructions`
   в клиенте игры; в CLI — `solana confirm -v`/разбор сообщения) и сверяет
   получателей с allowlist казны.
5. **Один подписант — один канал.** Приглашения подписать не принимаются по
   ссылке из личного сообщения; только из интерфейса Squads, открытого вручную.

Проверка при деплое: в `preflight-mainnet.sh` для mainnet требуется непустой
`MAINNET_AUTHORITY` (Squads-vault) — этот же мультисиг обязан быть источником
любых durable-nonce подписей, а не личный кошелёк разработчика.

## G-2. Ключи и права (пп. 44, 63, 64, 65)

| Роль | Требование | Проверка |
|---|---|---|
| Program upgrade authority | Squads-мультисиг, порог **≥ 3 из N**, независимые держатели | `solana program show` + `preflight-mainnet.sh` |
| `GameConfig.authority` | Тот же мультисиг (или отдельный governance-мультисиг) | `check-invariants.ts` + key inventory |
| `guardian` | Отдельный ключ, только `set_paused(true)` | событие `PausedToggled` |
| `reward_signer` | Выделенный low-priv ключ, **не** authority | `assertDedicatedPayer` |
| Epoch payer (hot wallet) | Отдельный кошелёк, баланс ≤ `PAYER_MAX_LAMPORTS` (0.5 SOL), пополнение траншами | старт бэкенда + алерты |
| RPC credentials | Отдельные ключи для браузера и сервера, ограничения по провайдеру | регламент |

- **Ротация:** при увольнении/смене подрядчика ротировать все ключи, которых
  человек касался; дату последней ротации — в приватный key inventory.
- **Хранение:** секреты — в KMS/HSM или аппаратном кошельке; запрещено:
  keypair в CI-артефактах, логах, чатах, бэкапах, образах контейнеров.
- **Разделение:** никто в одиночку не может и предложить, и исполнить вывод
  казны (propose → 30 с → execute + мультисиг).

## G-3. Апгрейд программы (пп. 45, 68)

1. `anchor build` дважды → сравнить `sha256sum target/deploy/solana_potato.so`;
   при расхождении сборка не воспроизводима и в прод не идёт. Публиковать
   `solana-verify`/Verified Build для внешней проверки.
2. Перед апгрейдом — прогон миграций **на форке мейннета** с реальными
   «старыми» аккаунтами: `migrate_config` / `migrate_field` / `migrate_epoch` /
   `migrate_admin_state`, затем чтение каждого аккаунта и сверка полей.
   Версия раскладки == размер аккаунта (белый список в `migrations.rs`,
   host-тест `current_layouts_are_the_terminal_entry_of_every_migration_whitelist`).
3. Апгрейд — через Squads (buffer → proposal → подписи → deploy), окно между
   созданием буфера и применением минимально.
4. После апгрейда: `scripts/check-invariants.ts` + интеграционный smoke
   (harvest на тестовом поле, ордер на маркете) + `watchtower` на события.

## G-4. Фронтенд и DNS (пп. 50, 67)

Для игрового хоста (`play.ares1.is-a.dev`) выставить те же заголовки, что на
лендинге (`landing/netlify.toml`):

```
Content-Security-Policy: default-src 'self'; script-src 'self';
  style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:;
  connect-src 'self' https://<rpc-host>; frame-src 'self' https://*.phantom.app https://*.solflare.com;
  object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
X-Frame-Options: DENY (или frame-ancestors 'none' при iframe-кошельках)
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

DNS: DNSSEC включён; 2FA + hardware key на аккаунте регистратора; мониторинг
смены NS/A/AAAA и CT-логов сертификатов; алерт на появление новых сертификатов
для домена. План отката: заранее подготовленный статус-баннер и альтернативный
домен для коммуникации при хайджеке.

## G-6. Мониторинг (пп. 49, 53, 65)

```sh
# крон, каждые 10 минут; exit 1 = инвариант нарушен → алерт
RPC_URL=<mainnet-rpc> PROGRAM_ID=<id> yarn tsx scripts/check-invariants.ts
```

Проверяет: authority минта = config PDA; freeze authority = none; decimals = 6
(POTATO и SKR); `supply ≤ max_supply`; `epoch.minted ≤ epoch.mint_cap`;
казна + квестовый пул ≤ supply.

Дополнительно мониторить:
- падение квестового пула (сибил-сигнал, риск R8);
- баланс hot-wallet (ниже 0.01 SOL — фатал, выше 0.5 SOL — предупреждение);
- события `PausedToggled`, `TreasuryWithdrawn*`, `AuthorityProposed`,
  `SkrMintUpdated` (watchtower + внешние алерты);
- неподтверждённые `roll_epoch` (лестница алертов 3/9/27 уже реализована);
- событие `GuardianUpdated` и ЛЮБОЕ изменение конфигурации мультисига
  (состав/порог) — алерт немедленно (п. 102: тихое понижение безопасности —
  это то, как KelpDAO потерял $292M: 2-of-2 → 1-of-1 без единого алерта).

## G-7. Параметры безопасности и источники данных подписанта (пп. 101, 102, 103, 117 — аудит 2026-09-28)

Прецеденты: KelpDAO ($292M) — верификаторы тихо понижены с 2-of-2 до 1-of-1;
Resolv ($25M) — облачный KMS скомпрометирован; GoonFi (п. 117) — ошибка
конфигурации цены эксплуатирована ботами в одной транзакции.

1. **Минимальные параметры безопасности — в коде, не в конфиге.** Всё, что
   сегодня зашито константами (`MAX_WITHDRAW_*_PER_WINDOW`,
   `WITHDRAW_TIMELOCK_SECONDS`, `ADMIN_UPDATE_TIMELOCK_SECONDS`, квота
   грантов 10 %), не имеет admin-инструкции изменения. Ввод любых
   настраиваемых «параметров безопасности» — только через двухшаговый
   таймлок 24 ч (как `update_skr_mint`), с алертом на саму попытку.
2. **Снижение любого порога безопасности — событие того же класса, что и
   смена authority**: обсуждается публично, проходит таймлок, анонсируется
   заранее. «Срочно, подписывай» — автоматически отказ.
3. **Второй независимый RPC-источник для подписанта обязателен до mainnet**:
   `RPC_URL_SECONDARY` от другого провайдера (не резервный endpoint того же
   вендора). Production по умолчанию не подписывает без сверки источников
   (реализовано в `apps/backend/src/policy.ts` + `epochRoller.ts`).
   Мониторинг (watchtower) уже читает данные независимо от подписанта.
4. **KMS/облако — не панацея** (Resolv): подпись в облаке допустима только
   при отдельном аккаунте/проекте под подпись, key policy с условиями
   (principal, время, сумма), минимальных IAM-правах, алертах на необычные
   `Sign`, отсутствии долгоживущих access-ключей, и при ончейн-инварианте,
   ограничивающем ущерб без подписанта (у нас: капы окна + двухшаговый вывод
   — уже в коде; новый «выпуск/минт» по подписи оффчейн без ончейн-лимита
   вводить запрещено).
5. **Изменение параметров цены/комиссий** (GoonFi): перед применением в
   mainnet — прогон на форке состояния с fuzz на границах (механика уже есть
   в G-3 для миграций; распространяется на любые admin-изменения) + выкат
   с ограничениями: kill-switch цена пресейл применима мгновенно, а повышение
   — только через 24 ч таймлок (реализовано), пулы цен программы не имеют.

## G-8. Казна, устройства и физическая защита подписантов (пп. 120, 121, 125, 126 — аудит 2026-09-28)

Прецеденты: Step Finance (компрометация устройств руководителей → 261 854 SOL);
Dominion Market (компрометация казначейского multisig 3-из-5 — три ключа
пали от одного фактора); Coldcard (слабый seed из-за прошивки); CertiK: 52
wrench-атаки за H1 2026.

1. Подписанты authority/казны — на **разных устройствах, ОС, вендорах и в
   разных местах**, чтобы один компрометирующий/принуждающий фактор не давал
   порог мультисига. Записать в key inventory (OPERATIONS) фактический
   разброс и проверять при каждой ротации.
2. Крупные казначейские движения — только через двухшаговый вывод программы
   (уже в коде) **плюс** паузу «на подумать» вне ончейна (правило «никаких
   срочных подписей», G-1b).
3. Никаких казначейских/authority ключей на рабочих ноутбуках руководителей
   и на машинах с повседневной почтой/мессенджерами.
4. Если появятся застейканные казначейские средства (Solana stake): мониторить
   `DeactivateStake` с казначейских аккаунтов как ранний сигнал вывода (стейк
   деактивируется не мгновенно — это окно для реакции). Сегодня стейкинг не
   используется; пункт активируется вместе с ним.
5. Duress-протокол и правила неразглашения персональных данных —
   [INCIDENT_RESPONSE.md](INCIDENT_RESPONSE.md) и OPERATIONS «Люди, устройства
   и доступ».
6. Происхождение каждого ключа — [KEY_PROVENANCE.md](KEY_PROVENANCE.md);
   ключи из затронутых версий прошивок = скомпрометированы.

|---|---|
| NFT-предметы (пп. 46, 47) | Сжечь update authority после финализации коллекции; `revoke` делегата в той же инструкции, что и возврат из стейкинга |

| Приём чужих/бриджнутых токенов как залог/ввод (пп. 97, 112 — Drift CVT/Rhea/Edel, Echo Protocol/rsETH) | Allowlist mint-адресов (уже: программа принимает только пиннутые `config.potato_mint`/`skr_mint` с проверкой decimals); новый листинг — таймлок + период остывания + минимум объёма/держателей; кап предложения внешнего токена + мониторинг; дисконт и выключатель |
| Session keys / делегаты / gasless-релееры (п. 109 — New Market Trading) | Ограничение по программе, сумме и сроку с возможностью отзыва; никогда не подписывать PDA от имени произвольных аккаунтов вызывающего; каждая сторонняя программа с полномочиями — аудит |
| Аллокации команды/фонда (п. 122 — Fogo Foundation) | Только on-chain vesting с лимитом высвобождения за период; крупные переводы — таймлок с отменой. Никаких «горячих» ключей с полной аллокацией |
| Пауза/таймлок/guard с новыми привилегиями (п. 110 — Gnosis Pay) | Adversarial-тесты пути паузы до включения фичи: попытка обойти guard подписью; учения по инциденту с замером времени до заморозки (INCIDENT_RESPONSE §5) |
| Сторонний скрипт/SDK на страницах с кошельком (п. 104 — Polymarket) | Только `script-src 'self'` (уже в CSP); любое исключение — SRI + отдельный origin для подписи; мониторинг хэша отдаваемого бандла; клиент контролирует состав инструкций (уже: txSafety) |
| ИИ-агент с кошельком / навыки / MCP (п. 130 — ClawHub) | Гейты аудита 71–82 + THIRD_PARTY_DEPENDENCIES §4: песочница без сети/секретов, пин хэшей, отдельная машина, ротация при подозрении |
| Переход POTATO/SKR на Token-2022 (пп. 38, 39) | Явный whitelist hook-программ; проверка отсутствия Permanent Delegate и Default Frozen; новый mint → `update_skr_mint` с проверкой decimals (уже в коде) |
