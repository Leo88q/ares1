## 1. Итоги в двух абзацах

Блокчейн-часть игры **не могла работать вообще**: код программы в репозитории не компилировался (несовпадения `#[instruction]`/аргументов), реферальная программа и миграции стояли вне `#[program]` и не были инструкциями, фронтенд строил `harvest` и `fill_order` с неверными списками аккаунтов (обе ключевые транзакции падали всегда), а бэкенд читал аккаунты по старому layout. Плюс три живые экономические дыры: клиентский выбор тира пресейла (EPIC всегда за цену дропа), неограниченный минт через реферальную награду (выплачивалась ещё и не тому адресату) и цена SKR-пресейла, читавшаяся из поля SOL-цены (0.25 SKR вместо 1053). Всё перечисленное исправлено в этом PR; оставшиеся риски (multisig authority, SKR-токен, RPC, CI) — в §1.3.

Экономика в целом здоровая для казуальной farming-игры: честный лаунч (100 % supply — из игры), все стоки сжиганием, эластичный дневной кап, растущий налог от supply. Главные риски — инфляционная спираль при оттоке (см. simulate.py: burn/mint падает к 0.26 к 12-му месяцу в старом моделировании) и отсутствие late-game стоков до M2 (стейкинг, сезонные поля). Модель `simulate.py` и `ECONOMY.md` устарели относительно текущих формул (прогрессивный налог, лунный цикл, комиссии 9–12 %) — пересчёт в §3.2.

### Чеклист безопасности (по программе)

| Проверка | Вердикт |
|---|---|
| **CEI** | Во всех мутационных инструкциях эффекты (статусы, счётчики, `last_harvest`) до взаимодействий (CPI). В `fill_order` — статус `Filled` и счётчики до SOL-перевода и token-CPI |
| **Overflow** | Урожай — u128 checked; счётчики — saturating; цены/комиссии — checked + `u64::try_from`; `overflow-checks = true` |
| **Access control** | `has_one = authority` на всех admin; `has_one = owner/seller/buyer` на ресурсах; двухшаговая передача authority; `initialize` фиксирует mint authority = config PDA и запрещает freeze authority |
| **PDA** | Все PDA — seeds + bump (bump хранится и проверяется); escrow-владение самим собой; коллизии исключены |
| **Arbitrary transfer** | Токены двигаются только: burn подписью владельца, mint подписью config-PDA (harvest/grant_reward — под капами), из escrow подписью escrow-PDA, из казны — по команде authority. Чужие токаны увести нельзя (реферальная ATA валидируется по mint + owner) |
| **Marketplace** | Self-trade запрещён; wash-trading убыточен (комиссия + SOL); front-running неактуален (фиксированная цена); TTL + permissionless close; кулдаун отмены 3 ч |
| **Эмиссионные инварианты** | Каждый минт учитывается в `epoch.minted_micro` и ограничен `max_supply_micro`; **после фикса C4** в `fill_order` минтов нет вовсе |

### 3.2 Дрейф модели: что пересчитать

`economy/simulate.py` и `ECONOMY.md` моделируют **старую** экономику: комиссия 3/6/9/12 %, фиксированный налог, без лунного цикла, эластичного капа, растущего налога от supply, мутаций, пресейла, рефералки. Текущая программа отличается:

| Формула | Старая модель | Текущая программа | Влияние на burn/mint |
|---|---|---|---|
| Комиссия рынка | 3–12 % | 9–12 % | burn с рынка ↑ (на типичных ордерах <1k 🥔: 3→9 %) |
| Tax harvest | нет (налог = еженедельный платёж-фикс) | 2–10 % с каждого урожая, ½ burn / ½ казна | новый постоянный sink, растёт с supply |
| Лунный цикл | нет | 0.85–1.15 × | нулевое среднее за цикл (не влияет на KPI, влияет на UX) |
| Эластичный кап | 250k фикс | 250k–750k (burn-бонус + utilization) | при активном burn кап растёт — эмиссия чуть гибче |
| Мутации | нет | Golden +25 % / Silicon decay÷2 | лёгкий рост yield у ~3 % полей (3 %) |

**Направленный вывод:** новый налог (даже 2 % на старте, ½ burn) + удорожание комиссии до 9 % повышают дефляционное давление относительно старым моделированием (burn/mint 0.59 за год). Точный пересчёт — задача M2-спринта (обновить simulate.py до текущих формул: 1 день = добавить tax(supply), lunar, fee 9–12, cap(elastic)).

**KPI остаётся прежним: burn/mint ≥ 0.6 по месяцу**, регулятор — `base_yield` в коридоре 3–8 🥔/день (правило: < 0.5 → −10 %, > 0.8 → +5 %).

### 3.4 Экономика пресейла (после фикса)

* Цена: 1053 SKR ≈ 2000 RUB (курс 1.90). Тираж 500, ≤5 на кошелёк.
* On-chain ролл 70/25/5: **EV множителя = 0.7×0.35 + 0.25×1.0 + 0.05×2.1 = 0.60×** (в единицах «Луг»), EV стоимости = 0.63× (в единицах 250 🥔) → ожидаемый ROI дропа ≈ 0.95× прямого in-game-покупки пропорционально — честный «дом с −5 %», джекпот EPIC (2.1×). Это маркетинговая механика, не yield — лендингу стоит показать EV, а не только «5 % EPIC».
* Распределение SKR: 80 % → казна, 20 % → buyback-кошелёк. **Он-чейн buyback-логики нет** (L7): buyback & burn POTATO — ручная операция (roadmap M4).
* SOL-пресейл: 0.25 SOL за модуль, явный тип (без гачи) — альтернатива для holders SOL.

### 3.5 Казна и монетизация

* Казна: 40 % комиссии + ½ harvest-tax. В старом моделировании ~148k 🥔/год при 1000 игроках — мало; основной SOL-кэш — пресейл (500 × 0.25 SOL = до 125 SOL при полном распродаже SOL-тиром; SKR-тир — в SKR) + реклама.
* Quest-казна: 550 🥔 пул одноразовых достижений (заполняется `init-onchain`), backend-квесты (100 🥔 старт, daily 5, ad 25) — лимит 500 🥔/день/пользователь, max 200 🥔/claim, он-чейн капа эпохи.
* `withdraw_treasury` — только authority (M1: мультисиг до mainnet).

### 3.6 Рекомендации (без изменений приоритетов, уточнения)

1. Обновить `simulate.py` до текущих формул **до** следующего регуляторного решения по `base_yield` (иначе решение на старых данных).
2. Late-game стоки (M2): стейкинг 🥔 → скидка налога, сезонные поля (тираж 1000), косметика — против инфляционной спирали (burn/mint → 0.26 к 12 мес. в старом моделировании).
3. Per-field дневной кап + bid-ордера (M2).

## 4. Технический аудит

### 4.1 Состояние репозитория до PR (корень проблемы «блокчейн не работает»)

1. **Программа не компилировалась** (C1) → devnet-бинарник (48D2…, слот 493194605) собран из **старшего** состояния кода; репозиторий и сеть разошлись.
2. **IDL отстал** от исходников (22 vs 29 инструкций) — часть новых фич (SKR-пресейл, лицензия, рефералка, ачивки) никогда не была в задеплоенном бинарнике.
3. **Фронтенд не соответствовал программе** (C6, H1, H3) — ключевые транзакции невалидны структурно.
4. **Бэкенд не соответствовал v2-layout** (C9) — после любого v2-деплоя backend ломается.
5. **Тесты не соответствовали коду** (H2) — `anchor test` не прошёл бы ни на старом, ни на новом коде без правок.

Вывод: «теплого старта» не было — был холодный запуск, где каждая из трёх частей (программа/фронт/бэкенд) собиралась из разных версий договорённостей.

### 4.2 Исправлено в PR

* Программа: все C-находки + `claim_achievement` paused + текст ошибки; `fill_order`/`buy_field_skr` переписаны с комментариями о бухгалтерии.
* Фронтенд: аккаунт-листы 1:1, v2-размеры, реальный epoch, SKR-проверки, рефералка, дроп из он-чейн.
* Бэкенд: v2-декодеры, size полей.
* Тесты: 30+ сценариев, включая supply-инвариант рефералки.
* Деплой-пакет: `warm-start-devnet.sh` (одна команда: airdrop → build → deploy/upgrade → IDL-sync → .env-patch → init-onchain → сводка), `init-onchain.ts` (идемпотентный: mint/config/epoch/presale/treasury_sol/quest-казна 550 🥔/SKR ATA + проверка SKR-mint), `migrate-v2.ts` (in-place upgrade v1→v2), CI-артефакты (.so + IDL).

### 4.4 Фронтенд (React)

* Архитектура поллинга ок: один `GameProvider` (20–30 c, пауза в скрытой вкладке, backoff ×2…×8), `dataSlice` для лидерборда, `getMultipleAccountsInfo`. Память: интервалы чистятся, `onAccountChange` подписки снимаются.
* TypeScript: strict + noUnusedLocals/Parameters; `any` — только в legacy-совместимых местах (в этом PR `useReferral` переписан без `any`).
* Мобильный/Telegram: viewport-fit, safe-area, MWA-адаптер; кошельки Phantom/Solflare.
* Доступность: aria-label, role=dialog/switch, aria-live для урожая (по прошлому аудиту, изменений не требовалось).

### 4.5 Бэкенд (Node/Express)

* Security-базис ок: Telegram initData верифицируется бот-токеном, привязка TG↔кошелёк 1:1, rate limit, in-flight блокировка claim, серверная on-chain верификация квестов, логи каждой выдачи.
* Ограничения: одно узло (JSON store), `trust proxy`, CORS по умолчанию `*` — для прода: лимит CORS на домен мини-аппа.
* `epochRoller` + `referralChecker` — cron'ы на nodе; если инстанс лёг — молча (T5/T6).

### 4.6 Деплой и окружение

* `deploy-devnet/mainnet/local.sh` + `init-onchain` — покрывают базовый сценарий; **новый единый вход — `warm-start-devnet.sh`**.
