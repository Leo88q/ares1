# Как правильно работать с данными в ARES-1 (рекомендация)

**Дата:** 2026-09-27 · **Ветка:** `arena/01a0e4f2-ares1`
**Основание:** замеры и инвентарь из [DATA_TESTS_AND_CAPACITY_2026-09-27.md](../../docs/DATA_TESTS_AND_CAPACITY_2026-09-27.md),
разбор референса в [STORAGE_REFERENCE_EXAMPLE_2026-09-27.md](../../docs/STORAGE_REFERENCE_EXAMPLE_2026-09-27.md),
гейты [MAINNET_LAUNCH_GATE.md](MAINNET_LAUNCH_GATE.md).

Документ отвечает на один вопрос: **как сделать слой данных игры качественным**, а не «какую БД выбрать».

---

## 1. Главный принцип: книга учёта уже есть — это цепь

Программа эмитит события на **все** денежные и властные действия: `Harvested`, `BatchHarvested`,
`RewardGranted`, `ReferralRewardPaid`, `TreasuryTaxed`, `TreasuryWithdrawn`, `TreasurySolWithdrawn`,
`TreasurySkrWithdrawn`, `AuthorityProposed`/`AuthorityAccepted`, `PausedToggled`, `SkrMintUpdated`,
`OrderCreated`/`OrderFilled`/`OrderCancelled`/`OrderExpiredEvent`, `ExportLicensePurchased`,
`AchievementClaimed`, `PresalePurchase` и т. д. — 30 событий по IDL. Watchtower сохраняет их
**только финализированными**, с проверкой слота, дедупликацией и fingerprint-сверкой; откатившиеся
транзакции помечаются `applied=false` и в проекции не попадают.

Отсюда правило, из которого следует всё остальное:

> **Офчейн-БД не может быть второй книгой правды про деньги.** Её задача — хранить то, чего в цепи
> нет и не может быть (намерения, обоснования, состояние до отправки транзакции), и **уметь сверяться**
> с цепью. Если БД и цепь разошлись — права цепь, а выдача останавливается, а не «докручивается» в БД.

Практический тест для любой новой таблицы: *«что произойдёт, если эту таблицу потерять полностью?»*
Если ответ «игроки потеряют деньги/предметы» — данные должны быть ончейн. Если «мы потеряем,
кто и зачем инициировал операцию и не отправим ли её второй раз» — это законное место для БД.

## 2. Что хранить офчейн (и почему именно это)

| Данные | Нужно ли в БД | Почему |
|---|---|---|
| **Интенты наград/выплат** (`nonce`, `expiry`, состояние до/после отправки) | **Да** | Требование гейта G-1: `grant_reward_once` + одноразовый nonce. Это единственные данные, которые **нельзя восстановить из цепи** после падения процесса: транзакция ушла, а процесс умер |
| **Аудит админ-действий** (кто, что, почему, какие проверки) | **Да** | В цепи есть «что» (`AuthorityProposed`, `PausedToggled`), но нет «почему» и «кто в команде» |
| **Квоты/антифрод клеймов** (квесты, рефералы) | **Да** | Ончейн-PDA защищает от повтора, но офчейн-лимиты (на кошелёк/сутки/кампанию) в цепь не положить экономично |
| **Курсоры сервисов** (`last_signature`, `last_slot`) | **Да** | Без них после рестарта — либо пропуск, либо дубль; паттерн уже отработан в Watchtower |
| **Сверка с цепью** (`reconciliation`, drift) | **Да** | Доказательство, что производные данные не разъехались с цепью |
| Балансы, прогресс, поля, ордера | **Нет** | Уже в цепи; дублирование создаёт второй источник правды и расхождения |
| Телеметрия/аналитика (DAU, воронки, ретеншн) | **Да, но** | Только из Watchtower-схемы, как проекция; не отдельная «игровая» БД |
| Клиентские данные (сессия, язык, настройки) | **Нет** | `localStorage`; персональные данные не нужны игру вообще |

## 3. Одна СУБД, два контура

Не «Postgres или SQLite», а **одна PostgreSQL, два логических контура и три роли**:

```
PostgreSQL
├── schema watchtower   — read-model цепи (УЖЕ ЕСТЬ): events, raw, cursors, reconciliation
│   ├── роль watchtower_migrator — DDL
│   └── роль watchtower_runtime  — SELECT/INSERT/UPDATE (без DELETE)
└── schema game_ops     — НОВОЕ: интенты, аудит, квоты, сверка
    ├── роль game_ops_migrator   — DDL
    ├── роль game_ops_writer     — INSERT/SELECT (+UPDATE только service_cursors)
    └── роль game_ops_reader     — SELECT
```

**Почему PostgreSQL, а не второй SQLite** (при том что SQLite отлично подходит для одиночного узла):

1. **Append-only можно обеспечить правами.** `REVOKE UPDATE, DELETE ON game_ops.reward_ledger FROM
   game_ops_writer` — и рантайм физически не может править историю. В SQLite ролей нет: любой процесс
   с доступом к файлу снимает триггер (`DROP TRIGGER`), а `INSERT OR REPLACE` обходит `BEFORE DELETE`
   при выключенном `PRAGMA recursive_triggers` — это проверено инструментом `yarn verify:sqlite`.
2. **Инфраструктура уже есть.** Миграции с `schema_version`, readiness, изоляция ролей, тесты против
   настоящего Postgres, docker-compose для бэкенда — переиспользуем, а не строим второй стек.
3. **Параллельные писатели и PITR-бэкапы** без «одного процесса-владельца файла».

SQLite остаётся разумным выбором, если сервис обязан быть одноузловым (например, офлайн-инсталляция).
Тогда обязателен компенсирующий набор: `chmod 600`, `recursive_triggers=ON` на каждом соединении,
HMAC-**цепочка** по строкам (не одиночные подписи), внешний якорь — то, что и проверяет
`verify-sqlite-immutability.mjs`.

## 4. Схема `game_ops` (эскиз)

```sql
-- Интенты наград: единственное место, где БД опережает цепь.
CREATE TABLE game_ops.reward_intents (
  id            bigserial PRIMARY KEY,
  recipient_ata text        NOT NULL,
  amount_micro  bigint      NOT NULL CHECK (amount_micro > 0),
  nonce         ubigint     NOT NULL,           -- тот же, что в PDA ["reward", recipient_ata, nonce]
  reason        text        NOT NULL,           -- «почему»: квест/кампания/ручное решение
  actor         text        NOT NULL,           -- кто инициировал
  state         text        NOT NULL CHECK (state IN ('pending','submitted','confirmed','failed','expired')),
  signature     text,                           -- подпись транзакции после отправки
  created_at    timestamptz NOT NULL DEFAULT now(),
  expires_at    timestamptz NOT NULL,
  CHECK (expires_at > created_at),
  UNIQUE (recipient_ata, nonce),                -- двойная выплата по одному nonce невозможна и офчейн
  UNIQUE (signature)                            -- одна подпись = один интент
);

-- Зеркало ончейн-факта: пишет только процесс-индексатор из финализированных событий.
CREATE TABLE game_ops.reward_ledger (
  id            bigserial PRIMARY KEY,
  intent_id     bigint REFERENCES game_ops.reward_intents(id),
  recipient_ata text        NOT NULL,
  amount_micro  bigint      NOT NULL,
  signature     text        NOT NULL,
  slot          bigint      NOT NULL,
  block_time    timestamptz NOT NULL,
  prev_hash     text        NOT NULL,           -- hash-chain: правка строки ломает цепочку
  row_hash      text        NOT NULL,
  UNIQUE (signature, recipient_ata)
);

-- Аудит: покрытие по операциям (INSERT/UPDATE/DELETE), а не «есть хоть один триггер».
CREATE TABLE game_ops.admin_audit (
  id           bigserial PRIMARY KEY,
  actor        text        NOT NULL,
  action       text        NOT NULL,
  subject      text        NOT NULL,            -- таблица/сущность
  params_hash  text        NOT NULL,            -- без чувствительных значений
  outcome      text        NOT NULL CHECK (outcome IN ('ok','denied','error')),
  created_at   timestamptz NOT NULL DEFAULT now()
);

-- Сверка: доказательство, что производные данные не разъехались с цепью.
CREATE TABLE game_ops.chain_reconciliation (
  id            bigserial PRIMARY KEY,
  stream_id     text        NOT NULL,
  finalized_slot bigint     NOT NULL,
  epoch_id      bigint      NOT NULL,
  granted_micro bigint      NOT NULL,           -- из Epoch.granted_micro (цепь)
  ledger_micro  bigint      NOT NULL,           -- сумма по reward_ledger (производная)
  drift_micro   bigint      NOT NULL,           -- 0 в норме
  checked_at    timestamptz NOT NULL DEFAULT now()
);
```

Роли: `REVOKE UPDATE, DELETE` на `reward_intents` (кроме перехода `state` — отдельная узкая функция
или view), `reward_ledger`, `admin_audit`, `chain_reconciliation`. Readiness сервиса — fail-closed:
если последняя сверка показала `drift <> 0` или её давно не было, сервис не становится ready.

## 5. Правила, которые делают данные качественными

1. **Идемпотентность по ключу цепи.** Ключ уникальности офчейн-записи должен совпадать с ончейн-PDA/nonce
   (`UNIQUE (recipient_ata, nonce)`). Тогда «повторить» операцию невозможно ни в одном из слоёв.
2. **Никаких `UPDATE` истории.** Состояние меняется вставкой новой строки или в отдельном поле-статусе;
   денежные строки неизменяемы и по правам (`REVOKE`), и по hash-chain.
3. **Fail-closed вместо самолечения.** Расхождение с цепью — стоп выдачи + алерт. Ни одна автоматическая
   «починка» БД по цепи не выполняется без человека: это скрытый класс ошибок.
4. **Один писатель на поток.** Как в Watchtower: row lock + CAS-версия курсора. Несколько процессов на
   один поток допустимы только как hot-standby.
5. **Миграции вперёд и явно.** Только версионированные файлы + `schema_version`, никакого DDL в рантайме
   (в Watchtower это уже правило). Перед миграцией — прогон на копии.
6. **Бэкапы проверяются восстановлением.** Бэкап без регулярного restore-дрилла — не бэкап. Ключи в
   бэкапы не попадают (`.gitignore`/`gitleaks` уже это обеспечивают).
7. **Никаких персональных данных.** Кошельки — псевдонимы; если понадобится аналитика по игрокам, хэш с
   солью и без адресов (в Watchtower это уже так).
8. **Наблюдаемость данных, а не только сервиса.** Метрики: глубина курсора, дрейф сверки, возраст
   последней финализированной записи, число `pending` интентов старше `expires_at`.

## 6. Неизменяемость: hash-chain + якорь (HMAC — только при необходимости)

Порядок предпочтений:

1. **Права** (`REVOKE UPDATE/DELETE`) — бесплатно и надёжно там, где есть роли (Postgres).
2. **Hash-chain** (`prev_hash`/`row_hash`) — ловит правку и удаление строки при доступе к БД.
3. **Merkle-корень суток/эпохи, запечённый ончейн** — единственный уровень, который не требует доверия
   к оператору БД; даёт внешний аудит и «доказательство клиенту».
4. **HMAC на строку** — нужен, если строки должен проверять тот, у кого **нет** доступа к БД (третья
   сторона, а также режим SQLite без ролей). Минус — управление ключом и версионирование формата.

Для `ares1` в конфигурации с Postgres достаточно 1–3; HMAC добавлять только под конкретную задачу
(например, «аудитор проверяет выгрузку без доступа к серверу»).

## 7. Производительность: это не узкое место

| Слой | Что показали замеры | Вывод |
|---|---|---|
| Декодер событий | 12 000–14 500 tx/с | с запасом |
| Запись read-model | ≥254 tx/с, 1 014 строк БД/с (нижняя граница на WASM-Postgres) | с запасом |
| Игровой БД-трафик (оценка: 10 000 DAU × 5 полей × 1 сбор/мин) | ≈0.6 tx/с в среднем | три порядка запаса |
| Ончейн | общий `epoch`/`config` PDA на каждый `harvest` | **вот здесь предел** |

Поэтому качество слоя данных в этой игре определяется не шардированием и не кэшами, а **корректностью,
сверяемостью и восстановимостью**. Оптимизировать БД под нагрузку, которой нет, — типичная и дорогая ошибка.

## 8. План внедрения (по фазам, без ломки текущего)

**Фаза 0 — сейчас.** Ничего не менять: у игры нет офчейн-состояния, `localStorage` + цепь покрывают всё.
Единственное, что стоит держать включённым, — Watchtower (read-model) и инвариант-монитор.

**Фаза 1 — только когда включаем рельс наград (гейт G-1).**
`game_ops.reward_intents` + `admin_audit` + роли/`REVOKE`. Никакого балансового учёта. Сервис-владелец —
**отдельный процесс без ключа** (паттерн изоляции Watchtower). Выдача — `grant_reward_once` с nonce-PDA.

**Фаза 2 — сверка и якорь.** `reward_ledger` как зеркало `RewardGranted` из финализированных событий,
`chain_reconciliation` (сравнение с `Epoch.granted_micro`), суточный Merkle-корень → ончейн-аккаунт.
Readiness fail-closed на дрейф.

**Фаза 3 — аналитика.** Лидерборды/воронки/ретеншн — запросами к схеме `watchtower` (или materialized
view), а не новой «игровой» БД. Если понадобится тяжёлая аналитика — read-replica, не второй источник.

## 9. Анти-паттерны (чего не делать)

| Анти-паттерн | Чем плохо |
|---|---|
| Хранить балансы/прогресс офчейн «для скорости» | Второй источник правды → расхождения с цепью и arbitrage-баги |
| Дать бэкенду с горячим ключом право писать в учётную БД | Расширение blast radius: угон процесса = правка истории |
| SQLite как авторитет по деньгам | Нет ролей: append-only держится только на триггерах, которые снимаются одним `DROP TRIGGER` |
| Вторая СУБД «опционально MySQL» под тем же доменом | Риск расхождения без выигрыша; нужно явно выбрать владельца записи |
| `UPDATE` истории для «исправления» | Уничтожает аудит; допустимо только `INSERT` новой корректирующей записи |
| DDL в рантайме, авто-миграции на старте | Непредсказуемые деплои; должно быть отдельным шагом с проверкой |
| Хранить ключи/HMAC-секреты рядом с файлом БД или в бэкапе | Подпись и шифрование теряют смысл |
| Автоматическая «сверка = починка» БД по цепи | Скрывает баги; расхождение — сигнал, а не задача для скрипта |

---

## 10. Итог одной фразой

**Цепь — книга учёта; БД — память о намерениях, обоснованиях и квотах, с обязательной сверкой и правами,
запрещающими правку истории.** Для ARES-1 это значит: сегодня — ничего не добавлять; при включении
наград — одна PostgreSQL-схема `game_ops` с интентами и аудитом, ролями без `UPDATE/DELETE`, сверкой
с `Epoch.granted_micro` и суточным Merkle-якорем ончейн.

Полный runbook (выкатка, проверки, инциденты, пределы) — `game/docs/DB_RUNBOOK.md`.

Что осталось за рамками реализации и почему: внешний якорь аудита (периодическая
запись `{count, max(id)}` вне БД) и ончейн-транзакция Merkle-якоря — это
операционные действия/часть механизма эпох, а не код слоя данных; без якоря
удаление строки аудита принципиально неотличимо от отсутствия события, и это
зафиксировано мутацией m5, а не замалчивается.
